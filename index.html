About me

I build tools that keep an engineer in the loop with a language model rather than handing the work over to one. The pattern I keep returning to is the same: the model drafts, deterministic code audits the draft against a written standard, and a human makes the call. The interesting engineering is in that second step — the part that never calls a model at all.

My current project is Resume Forge, a desktop application that produces OPM-compliant federal resumes. Its most useful component is the compliance scanner, which never touches the API: it parses the draft, measures it against the published hiring rules, and flags every violation instantly and for free. The model writes; the rule engine keeps it honest.

This site is itself a working example. The panel under Forge runs on your own API key, stores nothing on any server, and tells you exactly where your text goes before it goes there.

Resume

Engineering practice

  1. Resume Forge — desktop application

    2026

    Designed and built an Electron and React application that produces OPM-compliant two-page federal resumes and ATS-friendly private-sector resumes. Architected it in three layers with a hard security seam: a renderer with no filesystem, network, or secret access; a privileged main process that owns the OS keychain and every outbound call; and a pure-logic core with no Electron dependency, so the rule engine can be unit-tested and reused outside the app.

  2. Deterministic compliance scanner

    2026

    Wrote the component the project is built around: an auditor that never calls a model. It parses the draft resume and checks the two-page budget, the required per-position OPM fields, the header requirements, and orphan bullets against the parsed job announcement. Because it is deterministic it runs on every keystroke at zero cost — the model drafts, this decides whether the draft is acceptable.

  3. This portfolio — AI-assisted build

    2026

    Took an MIT-licensed template to a published site through a controlled AI-assisted workflow: written acceptance criteria first, a tracked issue, a feature branch, a reviewed plan, incremental commits, a human review of every generated change, and a documented test pass. The full prompt-and-response record is published in the repository.
